# DataSentry AI — 设计材料 01：需求一致性检查

> 依据《DataSentry AI 产品设计与开发 Prompt 完整版 v2.0》对全文 55 章做交叉一致性核查。
> 编号说明：本文引用采用新编号（一~五十五）；「四十三、最终任务」即用户所述的「四十」。
> 严重度：🔴 阻断（必须裁决后才能进入实施）/ 🟡 需注意（实施前明确约定）/ 🟢 建议（优化项）

---

## 1. 结论摘要

- 全文整体自洽性较好：核心公式（Priority Score、质量总分）、CLI 退出码、错误码、
  架构图、领域模型图相互之间无结构性矛盾。
- 发现 **4 个阻断级（🔴）**、**9 个注意级（🟡）**、**6 个建议级（🟢）** 问题，详见下表。

## 2. 阻断级问题（🔴，必须裁决）

### C-01 质量总分公式覆盖 6 维度，但文档定义了 8 个质量维度

| 项 | 内容 |
|----|------|
| 位置 | 九（9.1~9.9） vs 二十七（27.1/27.2） |
| 矛盾 | 九定义了 8 个维度（Completeness / Validity / Uniqueness / Consistency / Accuracy Proxy / Timeliness / Integrity / Distribution Stability），其中 9.5 Accuracy Proxy 与 9.8 Distribution Stability 是独立维度；但二十七的质量总分只含 6 个维度（无 Accuracy Proxy、无 Distribution Stability），且 9.9 明确写「质量总分按维度聚合」 |
| 影响 | 若 Accuracy Proxy 类 Issue（outlier、rare_category 等）无法挂靠到计分维度，分数解释力下降，且「按维度聚合」承诺落空 |
| 建议（待确认） | 方案 A：6 维度公式 + Accuracy Proxy 类 Issue 归入 Validity 或 Consistency（最省事，推荐）；方案 B：质量总分扩为 8 维度并重配权重。倾向 A，在 27.2 注明映射关系 |

### C-02 Priority Score 公式上限可超 100，与「0–100 分制」冲突

| 项 | 内容 |
|----|------|
| 位置 | 十二（12.8） |
| 矛盾 | 公式 = 10×severity + 25×confidence + 15×scope + 10×criticality_weight + 5×repro + 15×agreement + 10×novelty + 10×repairability。其中 criticality_weight 取值 0.6~1.6（12.4），取 critical 字段时 10×1.6=16，其余项取满后总分可达 106 > 100 |
| 建议（待确认） | 将 criticality 项改为 10×(criticality_weight−0.6)/1.0 归一化到 [0,10]，或全部计算后 clamp 到 100。推荐前者（保持可解释性） |
| 附带 | 12.8 示例「约 82 分」无法由公式精确复算（未给出 reproducibility/novelty/repairability 取值），建议实施时给出完整算例并写进单测 |

### C-03 两个地方出现不同 severity 权重取值

| 项 | 内容 |
|----|------|
| 位置 | 12.8 `severity_weight`（info=0.1, low=0.25, medium=0.5, high=0.75, critical=1.0） vs 27.1 `severity_norm`（info=0.05, low=0.2, medium=0.4, high=0.7, critical=1.0） |
| 矛盾 | 同名语义（severity 缩放系数）两套取值，后续维护极易改一处漏一处 |
| 建议（待确认） | 统一为一份 `SEVERITY_WEIGHTS` 常量，Priority Score 与维度得分共用；27.1 的 severity_norm 命名废弃 |

### C-04 数据契约与跨表检查的 MVP 边界互相矛盾

| 项 | 内容 |
|----|------|
| 位置 | 六（场景 F，多表关联审计，作为典型场景描述） + 11.11（跨表检测器已完整定义） vs 七（7.1 MVP 数据源仅单表导入；7.2 明确「多数据表关系检查」「数据契约」归 V1） |
| 矛盾 | 跨表检测器（orphan_foreign_key 等）与场景 F 在 MVP 无法落地（MVP 无契约、无多表工作区）；同时 11.11 的检测器若无契约声明（外键/对账表达式）根本无法运行 |
| 建议（待确认） | 明确：**跨表检测器与契约引擎整体划入 V1**（与 7.2 一致）；MVP 的六个连接器仅支持单表/单文件导入。场景 F 标注为 V1 场景 |

## 3. 注意级问题（🟡，实施前明确约定）

### C-05 性能预算口径不一致

- 20.4：1e6 行画像 < 20s；42.1（W3 DoD）：1e6 行画像 < 60s；3.1 KPI：100 万行画像 ≤ 60s。
- 三处目标值不一致（20s vs 60s）。建议：20.4 视为「优化目标」，42.1/3.1 视为「验收下限」，在 benchmarks/ 脚本中同时标注两档。

### C-06 严重度示例与默认值不一致

- 11.5 表格：「Standard Z-score 默认启用 = 否」与「Modified Z-score = 是」一致；
  但 11.5 正文与 11.4 的 excessive_null_rate 阈值（>0.05）与 42 验收无冲突。
  → 本条实际无矛盾，仅提示实施时以 11.x 各表为准，正文叙述不得覆盖表格默认值。

### C-07 表达式安全校验「白名单 vs 黑名单」并存

- 11.10 要求 AST **白名单**校验；14.3 给出危险表达式**黑名单**。
- 黑名单可被绕过（如编码混淆）。建议：以 AST 白名单为唯一校验手段，14.3 的黑名单仅作为
  快速预筛（拒绝并提示），并在 ADR 中记录该决策。

### C-08 Pydantic 模型清单不完整（引用了未定义类型）

- 18.2 中 `ScanConfig` 引用 `SamplingConfig`、`MaskConfig`；`ScanRun` 引用 `LLMUsageSummary`；
  16.1 `ColumnContract` 引用 `ColumnCheck` —— 均未在 18.2 或 16.1 中给出定义。
- 建议：Step 1（Domain models）补全这 4 个模型定义后再动工，并把「18.2 模型清单」设为
  Step 1 的验收基准。

### C-09 项目数据存储位置存在两套表述

- 23.1：SDK 默认在工作目录创建 `.datasentry/` 项目；51 章：首次启动自动初始化 SQLite
  于 `~/.local/share/datasentry/`。
- 建议：明确「全局配置/缓存（凭据、全局设置、LLM 缓存）→ 用户目录；项目数据（数据集
  元数据、扫描、报告、契约、审计）→ 项目工作区 `.datasentry/`」的二元布局，写入 ADR。

### C-10 Ollama 的 MVP/V1 归属

- 7.2 将「本地模型支持」列为 V1；17.5 架构图将 Ollama Provider 画在 MVP 架构中。
- 建议：MVP 实现 Provider 抽象 + OpenAI-compatible + Mock/None 三个实现；Ollama Provider
  作为 V1 实现，接口层（13.5/13.6）先行预留。架构图加注「Ollama 为 V1 实现」。

### C-11 4.1「不持久化用户原始数据」措辞歧义

- 字面与 17.3/52.1「项目数据默认存于用户指定工作区」、15.8「修复执行 = 生成新数据集版本」
  存在表面冲突。
- 建议：将 4.1 修订为「不向任何外部服务持久化/上传用户原始数据；本地持久化仅限于用户
  工作区内」。此条只在文档层面修订，不影响设计。

### C-12 「12 周计划」未覆盖 Phase 4/Phase 5 内容

- 三十三定义 Phase 4（历史与漂移）与 Phase 5（生态集成：GitHub Action、MCP、SARIF、插件）
  两个阶段；但四十四的 W1~W12 只排到 Phase 3（W11 修复闭环）+ Phase 6 部分（W12 演示/基准），
  **Phase 4、Phase 5 没有对应周次**。
- 建议：在 W12 之后的 4 周内排 Phase 4 + Phase 5（对应 48.2 的 1.0.0 阶段），在 12 周计划中
  加注「W13–W16（计划外）」，避免与 48.2 版本里程碑冲突。

### C-13 MVP 验收「至少 20 种数据质量检查」与 30 个 Issue 的 P0 范围需对齐

- 42 验收要求 ≥ 20 种检查；四十五中 P0 检测器（18/19/23/25/26）约覆盖 10+ 类；
  P1 的日期/字符串/类别族才是补齐 20 种的来源。
- 建议：把四十五中 #17、#21、#22、#24（日期、字符串、类别检测器）提升为 P0，保证
  第 6 周末（0.1.0 alpha）验收 ≥ 20 种检查成立。

## 5. 与原文无冲突、可放心执行的确认项

以下关键设计经交叉核对一致，无需改动：

1. **Priority Score 权重之和** = 10+25+15+10+5+15+10+10 = 100 ✅（除 C-02 的上限问题）
2. **质量总分权重** 27.2 与 27.1 公式一致（0.20/0.20/0.15/0.20/0.15/0.10 之和 = 1.00）✅
3. **CLI 退出码**（22 与 47.1）一致：0/1/2/3/4 ✅
4. **错误码前缀表**（47.2）与 24.2 一致 ✅
5. **LLM 预算**：13.9 `LLM_BUDGET_PER_SCAN = 20000` 与 18.2 `ScanConfig.llm_budget_tokens = 20000` 一致 ✅
6. **数据源清单**：7.1 六个数据源（CSV/Parquet/JSONL/XLSX/SQLite/PostgreSQL）与 49.3 的 MVP 列一致 ✅
7. **检测器默认启用**：11.5 稳健统计优先（Modified Z / MAD / Percentile 启用，Standard Z 禁用）与 8 章证据优先原则一致 ✅
8. **修复安全闭环**：15.8 新版本机制 ↔ 19 指纹 ↔ 3.1「回滚 100%」↔ 42「支持回滚」链路一致 ✅
9. **Prompt 五分区**（13.8/13.10）与 30.8 论文设计中的注入防御一致 ✅
10. **阶段 DoD**（42.1）与 12 周计划验收（44 章）逐周对齐（W3↔画像 60s、W4↔12 种检查等）✅
