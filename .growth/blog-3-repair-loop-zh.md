# 检测 → 修复 → 验证：数据质量闭环

大多数数据质量工具停在报告这一步：告诉你*哪里坏了*——一个分数、一张问题表、一条趋势线——然后你回到电子表格手工修。

DataSentry 最近十个版本（v0.31 → v0.40）就在做这件事：把**检测到修复**的闭环补完，并让修复侧批量到能扛住真实数据。

## 闭环

```
扫描 ──► 对比 ──► 提案 ──► 应用 ──► 回滚
  ▲                                       │
  └──────────── 验证 ─────────────────────┘
```

### 1. 扫描（与批量扫描）

`POST /scans` 扫描单个文件；CLI 支持逗号/换行/glob 批量路径（`datasentry scan "a.csv, b.csv, data/*.csv"`），每个文件以六维迷你条落进扫描列表。v0.39 起每次扫描都会记住**源路径**，下游所有表单自动预填——路径永远不用输第二遍。

### 2. 对比

`/ui/compare?runs=a&runs=b` 对比两次运行：六维差值、severity 变化、列漂移、schema 变更——以及按 `(问题类型, 列)` 分组的**问题级 diff**：NEW / FIXED / 持续三桶。

关键在：每个 NEW 组都带一个一键「propose repair」按钮，把该组的 issue id 和源路径直接送进提案引擎。两次扫描之间引入的回归，离修复只差一次点击。

### 3. 提案——什么都不写

批量提案拿勾选的问题（扫描详情页勾选列，表头支持全选）问规则引擎要修复方案。结果页按 **proposed / unsupported / error** 分组，标注操作、目标列、风险等级、预计影响行数。

刻意的设计点：**提案永不写数据**。没有自动应用、没有静默变更。规则引擎确定性、零 LLM 依赖，所以提案廉价、快速、可审计——但扳机永远由人扣动。

### 4. 应用——副本，绝不覆盖

`batch-apply` 执行所选提案。每个修复写出一份**修复副本** + `before` 快照，落在 `.datasentry/repairs/` 下。源文件永远不会被覆盖。这与单条工作台同款安全契约，只是扩展到 N 个问题。

### 5. 回滚——单条或批量

每次应用都是一笔事务：在修复历史页（`/ui/repairs`）回滚单条，或在批量应用结果页勾选多条 applied 一起回滚。结果页逐条报告 `rolled back` 或 `error`；历史页给出完整审计轨迹：run id、数据集、操作、行数、状态、时间。

## 为什么成立

- **批量 ≠ 鲁莽。** 批量提案只读；批量应用只写副本；批量回滚恢复快照。每个破坏性步骤都显式且可逆。
- **Diff 直达修复。** 对比页把两次扫描间的回归变成一次点击的修复提案——这正是质量工具通常停止「可行动」的地方。
- **审计默认开启。** 每个动作落进修复历史，状态转换可以验证，而不是只能信任。
- **本地优先。** 无云、无遥测——整个闭环跑在你的文件上，底下是 SQLite。

闭环合上了，而且是本地合上的。扫一份乱数据，对比两次运行，NEW 的问题离一个可逆的修复只差一次点击。
