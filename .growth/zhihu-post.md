# 知乎帖草稿

标题：**做数据质量工具两个月，我最后把"检测"和"AI"彻底分开了**

---

## 引子

数据质量这个领域不缺工具，缺的是"先看清问题"这一步。主流的 Great Expectations 是断言框架：你先定义规则，它帮你守着。Soda 走托管平台路线。两者都解决"已知规则下的回归"，但都默认你已经知道自己的数据哪里会坏。

我做了两个月数据质量工具（DataSentry，开源），最大的体会是：**大多数团队卡在"还不知道该断言什么"这一步**。数据是从各种渠道糊进来的，没人认真看过。这时候最需要的是一个"告诉我这数据有什么问题"的工具，而不是一个"让我先写配置"的工具。

## 我踩过的设计坑

**坑一：AI 应该放在哪一层。**

最早我也想过让大模型直接看数据然后报问题。很快意识到这是幻觉工厂——模型对数据的"印象"不是检查结果。最后定的架构是：39 个统计检测器（缺失、日期、编码、跨字段规则、外键、精确+模糊重复、Isolation Forest/LOF 离群）做确定性检测；LLM 只做三件事：把自然语言转成规则候选（带预演验证）、把问题翻译成业务语言、通过 MCP 让 agent 直接跑检查。

关键约束：**检测不依赖任何模型**。不配 LLM，全功能可用；配了 LLM，它永远碰不到原始 PII（进加密保险库），也永远不能改数据（人工审批）。

**坑二：修复闭环必须可回滚。**

`repair propose → preview → apply → rollback`：提案说清楚改哪几行；apply 时写带指纹的副本 + 回滚产物。任何自动化修复的爆炸半径 = 一个文件、一次运行、随时可回滚。

**坑三：证据链比结论重要。**

一个发现应该长这样："order_date 列有 9 个值不符合 ISO 格式、5 个是不存在的日期，置信度 99.5%，占 4.5% 行"——样本、占比、置信度都在，你可以质疑阈值，但没法质疑计数。

## 一些诚实的局限

- 离群检测器（Isolation Forest/LOF）是为表格数据调的，奇怪分布会误报——所以置信度必须暴露出来
- 模糊重复的阈值要按数据集调
- Web UI 是能用，不是好看
- 单作者项目，成熟度靠 1229 个测试和 95% 覆盖率撑着，但生态远没法和 GE 比

## 为什么开源 + 为什么本地优先

数据不出机器（可接本地 Ollama），DuckDB 执行引擎，`pip install` 三行命令就能跑。常见的数据质量问题是"仓库里一个 CSV 就能复现"的问题，不该为此引入一个平台。

GitHub：https://github.com/Jackxiaozhiren/datasentry （Apache-2.0）
